# Decisions

Choices the spec left open, what was picked, and why. Every feed sits behind an adapter, so any provider choice here is reversible without touching the engines.

| # | Decision | Why |
|---|---|---|
| 1 | **TypeScript end to end** (Fastify API + worker, Next.js PWA, engines as TS packages). | One type system from the feed adapter to the pixel: the contract types in `packages/contracts` are imported by every package, so a schema change fails the build everywhere it matters. Python engines would have meant a second copy of every type. |
| 2 | **No build step for packages**; they export `src/*.ts` and run under `tsx`. | Fewer moving parts and no stale `dist/`. The API is not CPU-bound; startup cost is paid once. |
| 3 | **Engines are pure functions**: state in, output out, `now` passed as an argument. The worker reads the store, calls engines, writes results. | This is what makes the 90-day replay and the calibration page honest: the replay calls the exact same functions as the live loop with historical state. It is also the spec's boundary ("engines never call feeds directly") enforced by construction. |
| 4 | **Next.js static export served by the API from one origin.** | The PWA, the service worker, web push and the session cookie all want a single origin. One deployable, one HTTPS certificate, no CORS. The UI has no server-side logic to lose: it only renders what the API returns. |
| 5 | **Documents as `(id, ts, instrument, status, doc jsonb)` tables**, one per collection, validated by zod at the boundary; candles and data points as proper time-series tables (Timescale hypertables when the extension is present, plain Postgres otherwise). | The journal's shapes will change as the system learns; jsonb with typed boundaries keeps migrations cheap while the hot path (candles) stays columnar. |
| 6 | **Two store implementations** (`PgStore`, `MemoryStore`) behind one interface with a shared conformance suite. | The system boots and every test runs with zero infrastructure; production uses Postgres. |
| 7 | **Scheduler and bus degrade gracefully**: BullMQ and Redis pub/sub when `REDIS_URL` is set, in-process timers and an EventEmitter otherwise. | Runs on one small machine with no Redis; scales out when Redis is added. |
| 8 | **Free data first**: Yahoo chart API (candles; CME futures are delayed), TradingView scanner (near-real-time quotes and yields), TradingView economic calendar (consensus, prior, actual, with history), FinancialJuice RSS (headlines), Kalshi and Polymarket public APIs, Coinbase, CBOE delayed option chains, CFTC. Paid adapters (Polygon, Databento, Tradier, Alpaca, Trading Economics, Benzinga, FRED) are written against the documented APIs and switch on when their key is present. | Spec: "must work with zero paid keys and get better when keys are added." All free sources were verified reachable on 2026-11-21. |
| 9 | **Recorded market data is committed** under `data/recorded/` (raw provider payloads, gzipped, ~22 MB). | Yahoo keeps 1-minute history for 7 days only. The Nov 16 and Nov 17 2026 sessions the spec names as fixtures had to be captured on Nov 21 or lost. The replay, the historical-reaction tables and the watcher base rates are all computed from this archive, so they are reproducible. |
| 10 | **The "synthetic replay" replays real prices and real releases.** Nothing in the calibration page is simulated price data; "synthetic" refers only to the calls being generated after the fact rather than live. Replayed calls are tagged `replay` and the calibration page says which source it is showing. | A calibration chart built on made-up data would be worse than an empty one. |
| 11 | **Fed pricing derived from Fed funds futures** with the standard FedWatch method, cross-checked against Kalshi, instead of scraping the CME FedWatch page. | The CME page is script-rendered and bot-protected; the futures-implied method is what FedWatch itself publishes, and it is reproducible. |
| 12 | **Memory layer is a local TF-IDF vector index** with structured filters, behind an `Embedder` interface. | Works with no external embedding key; a hosted embedding model can replace it without touching callers. Journal questions are mostly about dates, instruments and tags, where lexical vectors plus filters retrieve precisely. |
| 13 | **Every LLM use has a deterministic fallback** (rule-based headline classifier, template prose, rule-routed Ask). LLM answers are validated (as-of stamp, probability and kill condition with any direction, every number traceable to the fact sheet) and replaced by the rules answer if validation fails. | The desk must work with zero keys, and a model that invents a number is worse than a template. |
| 14 | **Single-user passphrase auth** (`DESK_TOKEN`, signed httpOnly cookie). | One trader; the URL is public; the journal is private. No account system to maintain. |
| 15 | **Firm rules: the spec's numbers are the seed of record**, stamped `trader spec 2026-11-21`. Anything the spec did not state is either read from the firm's own help center (URL recorded) or left null and marked unverified, in which case sizing on that account is blocked until confirmed. | A sizing engine built on a guessed drawdown is the exact failure this system exists to prevent. |
| 16 | **The system never places orders** and has no broker write path. Positions and fills are entered manually or arrive from a read-only account feed. | Spec section 1. |
| 17 | **Trader timezone defaults to America/New_York**, overridable with `DESK_TZ` or in `profile.yaml`. | The spec says "local" without naming a zone. |
| 18 | **TradingView data enters three ways**: the public scanner (quotes), webhook alerts (`/api/hooks/tradingview`, real-time candles pushed by the trader's own TradingView alerts), and chart-export CSV import. No scraping of a logged-in TradingView session. | The first two give near-real-time data within TradingView's intended interfaces; a headless logged-in session would be brittle and against their terms. |
